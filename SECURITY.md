# Security

This repository builds a static website. There is no server, no database, no
user accounts, no contact form, no cookies and no session state — which removes
most of what is normally attacked. What remains is the supply chain, the
repository itself, and what the delivered page is allowed to do in a browser.

## Reporting a vulnerability

Email **hkggroups@gmail.com** with the detail and how to reproduce it. Please
do not open a public issue for a security problem, and please do not test
against the live site in a way that degrades it for other people.

You will get an acknowledgement. If the report is valid I will fix it and, if
you want, credit you.

Out of scope: anything that requires the visitor's own machine to already be
compromised; missing HTTP response headers that GitHub Pages does not allow me
to set (see below); reports generated by a scanner with no working
proof-of-concept.

## What protects this site today

**Delivery.** GitHub Pages serves everything over HTTPS with HSTS, and HTTP
requests are redirected. There is nothing else to reach.

**Content Security Policy.** Declared in `index.html` as a `<meta>` element,
because a static host cannot set response headers. It restricts scripts to this
origin plus the two known third parties, pins the one inline script by SHA-256
hash rather than allowing inline script generally, blocks plugins and
`<object>`, forbids form submission, and pins `<base>` to this origin.

**No third-party JavaScript by default.** One analytics beacon, cookieless,
skipped entirely when the visitor sends Do Not Track, and absent from the
build unless a token is configured. No tag manager, no ad script, no embeds,
no social widgets.

**Nothing secret in the repository.** The only build-time variable is a
Cloudflare beacon token, which is public by design — it appears in the page
source of every site that uses it. There are no API keys, credentials or
private endpoints in this project, so there is nothing here to leak.

**Supply chain.** Dependencies are installed with `npm ci` from a committed
lockfile, so a build cannot silently pick up a newer version. Dependabot
watches npm packages and GitHub Actions for known vulnerabilities
(`.github/dependabot.yml`). The workflow runs with `contents: read`.

**Content integrity.** The site is fully prerendered at build time from files
in this repository. There is no runtime content source that could be tampered
with, and no user input is ever rendered — the one use of
`dangerouslySetInnerHTML` takes HTML compiled from Markdown in this repo, which
is documented where it happens.

## The honest limits

**HTTP response headers cannot be set on GitHub Pages.** That means no
`X-Content-Type-Options`, no `Permissions-Policy`, and — the one that matters —
no `frame-ancestors`, which is ignored when CSP arrives in a `<meta>` element.
So this site can be framed by another site. For a static portfolio with no
authenticated actions there is nothing to clickjack, which is why this is
accepted rather than worked around. Moving hosting to a provider that supports
a headers file (Cloudflare Pages, Netlify) would close it.

**A public repository is readable by everyone.** That is intended — see
`LICENSE`, which grants no right to use what you can read. Protection here is
legal, not technical, and it always will be for a website: any site's code is
delivered to every visitor.

## Recommended repository settings

These are account settings, not files, so they are not in this repository.
Worth having all of them on:

- Two-factor authentication on the GitHub account.
- Branch protection on `master`: no force-push, no deletion.
- Secret scanning and push protection enabled.
- Dependabot alerts and security updates enabled.
- Signed commits, if you want authorship to be cryptographically provable as
  well as recorded.
